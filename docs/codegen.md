# SETEP code generation

`setep file.setep --python` writes `file.py` and the shared `setep.py` runtime.
`setep file.setep --chakra` writes distributed Chakra execution traces for
ASTRA-sim. `setep file.setep --onnx` writes an ONNX model (see `onnx.md`). All
three start from the same parser and semantic lowering; the language itself is
specified in `SETEP.txt`.

## Pipeline

`src/SetepParser.*` is generated by the JimJam parser generator from
`grammar/Setep.jim` (tokens) and `grammar/Setep.jam` (rules). `SetepSyntax.*`
normalizes the parse tree. `SetepSemantic.h` defines a parser-independent tensor
program: expressions, assignments, structured loops, functions, inputs, and
results. `SetepSemantic.cpp` resolves lexical tensor references and transfers,
lowers arithmetic in source order, retains repetition as loops, and
(`lowerPartitions`) expands shape partitions into physical tiles. Backends:

| backend | source | input |
|---|---|---|
| PyTorch | `SetepPython.cpp`, `SetepPythonRuntime.h` (the `setep.py` text) | behavioral IR |
| Chakra | `SetepGraph.cpp` (operation graph), `SetepDistribution.cpp` (placement), `SetepChakra.cpp` (writer) | partition-lowered IR |
| ONNX | `SetepOnnx.cpp` (JSON request), `python/setep_onnx.py` (graph builder) | partition-lowered IR |

No backend recognizes model names.

## PyTorch source

Each computation definition becomes a model method. The last definition is
called by `forward`. Explicit tensor names become local variables; omitted names
receive generated local names. Functions returning multiple tensors use a Python
dataclass with named fields. Input tensors and residuals are preserved; every
arithmetic result is a new value. Single-use anonymous results are initialized
directly under their SETEP destination names. This removes redundant tensor
copies without moving the computation, duplicating calls, or renaming
loop-carried and explicitly named values.

Dotted input names denote members of a structured input, not slices of a tensor.
For example, `A.TOKEN_IN`, `A.IMAGE_IN`, and `A.VIDEO_IN` become fields of a
computation-specific input dataclass. The generated method takes one `A`
argument. Each field retains its own shape; the fields are not concatenated or
required to have matching dimensions. Aggregate arguments also pass through
calls to other generated computations.

A computation may contain scalar and tensor declarations alongside expressions.
Declarations apply throughout that computation, shadow global declarations, and
do not leak into other computations. Scalar constants and tensor metadata are
emitted with computation-qualified names. Required data-size labels remain
metadata and do not change the demo dtype.

A choice such as `CHOOSE?SEL(){A+A | A+A+A}` calls the selector computation
`SEL` once for each zero-based alternative, always with the original scope
input: `SEL(self, choice_index, value, repetition=None)`. With an indexed
selector (`?SEL[]()`), `repetition` carries the current repetition index and the
enclosing instance path. The hook returns a tensor holding 1 (selected) or 0.
Exactly one alternative must be selected; the demo selector chooses the first.

### Weights and instance paths

Weights are model members named after their lexical definition/scope and SETEP
weight name. A lower-name definition with a single untyped literal is a scalar;
with `@dtype` it declares a weight shape, even when it has only one dimension.
Global and computation-local weight declarations are retained as `WEIGHT_SHAPES`
and `WEIGHT_DATA_SIZES`. Each model-owned bank stores its declaration; the demo
allocates every instance with that shape. Python weight banks are `nn.Module`
children containing registered `nn.Parameter` values, so parameters participate
in autograd, `state_dict`, optimizer traversal, and device/dtype conversion.
Populate them before creating an optimizer. No weights are invented or allocated
during `forward`; an absent weight raises an error.

Generated methods accept `instance_path`, a tuple of enclosing instance indices.
Every repeated scope appends its loop index, including nested, peer, and reverse
scopes. A nested scope uses `(outer, inner)` relative to the caller's path. On
scope exit the parent's path is restored.

Only array weights are keyed by this path. A weight declared as an array
(`q[layers] = ...`) or read as `w[n]` has one value per instance: `q[]` selects
the current repetition's element, and an unindexed array weight takes the
instance of the enclosing indexed call, so `MLP[]()` reads its own layer's `up`
by plain name. Any other weight has one value, keyed by the empty path,
wherever it is used, even inside a repeated scope; per-layer weights must
therefore be declared as arrays.

Calls receive the current scope path. An arrayed definition additionally appends
its generated `NAME_family` tag and loop index; an arrayed weight appends its
current instance index. Thus dense layer 0 and MoE layer 0 retain distinct
parameter identities. For example:

```python
for layer in range(12):
    model.weight_q.set((layer,), q_weights[layer])
```

Weights are always persistent, so `!` on a weight is rejected ("remove ! from
weight"); `!` marks persistent tensors only.

### Opaque computations

An empty definition such as `EMBED(IDS:TABLE) {}` declares an opaque
computation. Its parameters fix the inputs each call passes and name the
generated hook's arguments; the outputs follow from where the result goes, so
`TOKENIZE(TEXT) {}` used as `TEXT >> TOKENIZE() >> IDS:MASK:POSITIONS` has three.
With no parameters (`RANDOM() {}`) the hook takes no tensor and the result must
reach a declared tensor, which gives its shape. Multiple outputs are returned in
named dataclasses. The generated model exposes opaque computations as
overridable methods; they contain a not-implemented comment and return
zero-filled, shape-preserving demo tensors.

Every opaque call supplies the current `instance_path` and an `occurrence` name
derived from its lexical owner, operation, and occurrence number. For example,
GPT-2's block calls use `CHATGPT2_INFERENCE_BLOCK_LN_0` and
`CHATGPT2_INFERENCE_BLOCK_LN_1`, each with `(layer,)`; the final normalization
uses `CHATGPT2_INFERENCE_LN_0` with `()`. These identities are independent of
temporary variable numbering and copy elimination. Key registered parameters or
modules by both the occurrence and the path to keep blocks and separate
operations distinct:

```python
def LN(self, value, instance_path, occurrence):
    key = occurrence + "_" + WeightBank.key(instance_path)
    return self.norms[key](value)  # norms is a prepopulated nn.ModuleDict
```

Supply implementations of embedding, normalization, activation, sampling, and
other opaque operations in a subclass. `models/chatgpt2/chatgpt2_impl.py` is a
handwritten subclass of the generated GPT-2: embeddings, per-occurrence layer
normalization, causal scaled attention softmax, GELU, and greedy next-token
selection, with tiktoken's GPT-2 encoding for `TOKENIZE` / `DETOKENIZE`. Pass
`--weights gpt2.safetensors` (see `eval/gpt2/make_checkpoint.py`) to load a
checkpoint; the loader validates shapes before copying values. Install its
dependencies with `python -m pip install -r models/chatgpt2/requirements-chatgpt2.txt`.

### Persistent state

Persistent tensors such as `K!` and `V!` use model-owned `StateBank` instances,
separate from ordinary `K` and `V` locals and from trainable weights.
Corresponding named scopes share their state across functions; named repetition
indices identify individual layers, while anonymous decode-loop indices do not
create fresh caches. `K >> K!` replaces state; concatenating the state with new
rows and transferring the result back appends (for example
`K!^:X^ >:> NEXT; NEXT^ >> K!`). Reading uninitialized state raises an error;
`model.reset_state()` clears it.

### Runtime and demo

`setep.py` contains the WeightBank/StateBank classes, arithmetic, shape
inference, placeholder, logging, normalization, masked attention, cross-entropy,
local vector-Jacobian products and SGD helpers. Generated models import it and
keep their own shape metadata; several models can share one copy.

Running a generated model (`python chatgpt2.py`) executes a synthetic CPU demo:
a shape-only pass solves matrix, residual, split and merge dimension constraints
from the declarations, then seeded random weights are registered for every
required instance and the model runs under `torch.no_grad()`. Opaque functions
are placeholders, so the output is not a trained model prediction. Pass
`--debug` to print model progress and operation sizes (`setep.set_debug(True)`
from library code).

### GPT-2 training

`chatgpt2_training.setep` describes a forward pass, reverse layer traversal,
explicit backward computations, and SGD weight assignments. `eta` is a scalar
multiplier, not a weight. Python updates copy into registered parameters,
preserving tied weights and optimizer references.
`models/chatgpt2/chatgpt2_training_impl.py` implements the training opaque
computations with real PyTorch gradients:

```text
setep models/chatgpt2/chatgpt2_training.setep --python -o out
cp models/chatgpt2/chatgpt2_training_impl.py out/
python out/chatgpt2_training_impl.py --weights gpt2.safetensors --learning-rate 0.0001 --steps 2 "Paris is the capital of France."
```

Add `--save-weights trained.safetensors` to save the final weights in GPT-2
format.

## Chakra execution traces

`setep model.setep --chakra` elaborates the partition-lowered program into an
operation graph (every repetition, array element and alternative expanded), places
it on a processor inventory, and writes one trace per occupied processor:

```text
out/model.0.et
out/model.1.et
...
out/model.chakra.json
```

Pass the prefix, without `.0.et`, to ASTRA-sim:

```text
--workload-configuration=out/model
```

**Inventory.** `--nodes` x `--processors-per-node` accelerators, each with
`--memory-mb` of memory, plus optional `--hosts-per-node` host processors
(`--host-memory-mb`). Every SETEP operation runs on an accelerator; hosts are
listed in the inventory but receive no operations.

**Placement.** Deterministic next-fit packing in operation order: once an
operation does not fit, that processor is closed and placement continues on the
next one, without backfilling. Weights are charged once per processor and
activations, inputs and caches once per sequence; storage shared by several
operations (a weight read twice, an activation read by its consumer) is charged
once. An operation larger than one processor is rejected. `--replicas N` places N
complete copies on disjoint processors (0 places as many as fit);
`--sequences N` instantiates N sequences per replica on the same processors.

**Traces.** Each rank contains its placed compute nodes. Dependencies within a
rank remain local; dependencies across ranks become matching send/receive nodes
with the same source, destination, tag, and payload bytes. Multiple consumers on
the same destination rank share one producer-output transfer. Each consumer waits
for that rank's receive; no dependency ID refers to a node in another file.
Replica and sequence instances have distinct IDs and communication tags. The
traces preserve the operation graph's communication; they do not add training
collectives or synchronization between independent replicas.

Compute nodes carry `num_ops` (arithmetic) and `tensor_size` (bytes read) for
ASTRA-sim's roofline model, input and output tensor shapes and dtypes, and
`setep_operation_id`, `setep_replica` and `setep_sequence`. The node duration is
the modeled effort in whole microseconds (rounded up, minimum one):
`ops / gflop-per-cycle + (read MB + write MB) / mb-per-cycle + overhead + 1`
cycles at `--clock-hz`.

The manifest records the rank count, each rank's address (`[0, node, slot]`),
processor type, memory capacity and resident memory, the replica and sequence
counts, and the clock. Configure ASTRA-sim's network for `num_ranks`. A later
export with fewer ranks removes obsolete numbered trace files for the same
prefix. `tools/chakra_trace.py` decodes the traces with the standard library
only (`summary`, `check`, `compare`).

The file naming follows the
[ASTRA-sim workload input convention](https://astra-sim.github.io/astra-sim-docs/getting-started/argument-workload-config.html),
and records use the
[Chakra protobuf schema](https://github.com/mlcommons/chakra/blob/main/schema/protobuf/et_def.proto).
